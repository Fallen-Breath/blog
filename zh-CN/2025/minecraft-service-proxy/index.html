Minecraft 连不上认证 Mojang 认证服务器的一种解决方案：HTTP 转发

发表于 2025-03-09 更新于 2026-11-16 阅读次数： 本文字数： 6k 阅读时长 ≈ 11 分钟

背景

由于众所周知的网络环境，国内连接 Mojang 的官方认证服务时，总容易遇到抽风情况，包括但不限于正版登录时出现“认证服务器宕机”之类的报错。 万一遇到 Mojang 使用的微软云被区域性 DNS 污染，那影响范围就更大了

您可能是正版软件的受害者

如果遇到的是服务器列表一直 ping 不通、或一直卡在“正在连接至服务器…”界面，那是连接建立之前的问题，可以看看 Minecraft 连接服务器速度优化

快速判断方式

这里有一些常见的“连不上 Mojang 的官方认证服务”的报错与对应原因，可供参考

客户端请求 session 服务失败

玩家进服时，客户端会调用 Authlib 的 joinServer 接口向 Mojang 登记本次会话。若请求失败，客户端会以翻译键 disconnect.loginFailedInfo.serversUnavailable 生成原因，并嵌入外层翻译键 disconnect.loginFailedInfo 中断开连接。屏幕显示的完整文案随客户端版本变化如下：

客户端版本 中文文案 英文文案
1.14.4 ~ 1.16.5 登入失败：身份验证目前正在停机维护。 Failed to log in: The authentication servers are currently down for maintenance.
1.17 ~ 1.17.1 登入失败：暂时无法连接到认证服务器，请稍后再试。 Failed to log in: The authentication servers are currently not reachable. Please try again.
1.18 登录失败：暂时无法连接到认证服务器，请稍后再试。 Failed to log in: The authentication servers are currently not reachable. Please try again.
1.18.1+ 登录失败：暂时无法连接到身份验证服务器，请稍后再试。 Failed to log in: The authentication servers are currently not reachable. Please try again.

玩家进服时，开启正版验证的服务端会调用 Authlib 的 hasJoinedServer 接口向 Mojang 核验玩家会话。若请求失败，不同服务端的报错表现如下：

原版服务端与 Velocity 会下发翻译键 multiplayer.disconnect.authservers_down，由玩家的客户端按自身版本和语言显示：

客户端版本 中文文案 英文文案
1.14.4 ~ 1.18 认证服务器处于宕机状态中。请稍后再试，抱歉！ Authentication servers are down. Please try again later, sorry!
1.18.1 ~ 1.21.8 身份验证服务器目前处于宕机状态。请稍后再试，抱歉！ Authentication servers are down. Please try again later, sorry!
1.21.9+ 身份验证服务器目前处于宕机状态。请稍后再试。抱歉！ Authentication servers are down. Please try again later. Sorry!

BungeeCord 则使用自带的 mojang_fail 配置项，默认文案固定为：

  • Error occurred while contacting login servers, are they down?

解决方案

目前常见的，用于解决 Mojang 认证服务器无法访问的方案，有如下几种

  1. 借助魔法来访问 Mojang 认证服务器

    1. 优势：专业的事情交给专业的工具做，跑起来效果好
    2. 缺点：获取 / 搭设魔法存在门槛；服务端不一定支持

  2. 使用修改 DNS / host 文件的方式，直接访问 Mojang 的服务

    1. 优点：无需额外资源设备；操作较为方便；对任意 MC 客户端 / 服务端均生效
    2. 缺点：核心思想是在本地做 DNS 解析。仅能有效解决 DNS 污染问题，无法较好解决网络连接质量不佳的问题；硬编码的 DNS 解析项可能具有时效性

  3. 使用修改 DNS / host 文件的方式，指向自建的 TCP 转发服务

    1. 优点：对 MC 客户端 / 服务端无侵入，兼容性好；同时能解决网络连通性问题
    2. 缺点：需搭设转发服务；由于仅工作在四层，只能按目标地址或 SNI 整站转发，无法限制具体的 HTTP 请求内容，转发服务容易被滥用

  4. 搭设 Mojang 认证服务器的 http 转发服务器，并让 MC 使用这一转发服务器

    1. 优点：类似魔法，搭起来效果很好
    2. 缺点：搭设转发存在门槛，且 26.3+ 还需改写 discovery 接口返回的响应内容，不能只做单纯的反代；低版本 MC / 特殊的服务端不一定支持；需信任转发服务器

对于第一种方案，原版 mc 的客户端可以用参数指定 authlib 走 socks，但服务端不支持； 至于 velocity bungeecord 这俩代理端，之前我搞过两个 fork，给他们增加了相关魔法能力， 若有需要可以参考下：https://github.com/TISUnion/Velocity, https://github.com/Fallen-Breath/BungeeCord

对于第二种方案，可以参考 cv12264962、 cv15851058 这两篇专栏

对于第三种方案，可以用 gost、haproxy 或 sniproxy 等工具搭设 TCP 转发，再配合本地 host 或自建 DNS 将 Mojang 域名指向转发服务器

对于第四种方案，我以前水过一个 相关的动态。同时，这也是下文会提到的方案

麻将服务器列表

先看看有哪些 Mojang 服务是需要转发的

从 1.14 开始统计，原版 MC 里，会使用 authlib 访问如下几个 Mojang 提供的服务

  1. auth，https://authserver.mojang.com，可使用 -Dminecraft.api.auth.host 配置。用于旧版正版登录相关。高版本已不再使用，且此地址目前也已无法访问。不过低版本仍需要把此配置带上，才能让转发配置生效
  2. account，https://api.mojang.com，可使用 -Dminecraft.api.account.host 配置。用于旧版查询玩家档案信息等
  3. session，https://sessionserver.mojang.com，可使用 -Dminecraft.api.session.host 配置。用于进服时的会话登记与正版验证，正版验证入服必备
  4. services，https://api.minecraftservices.com，可使用 -Dminecraft.api.services.host 配置。用于获取公钥、玩家属性、聊天举报，以及部分版本的玩家档案查询等
  5. profiles，https://api.mojang.com，可使用 -Dminecraft.api.profiles.host 配置。用于按名称查询玩家档案信息
  6. discovery，https://discovery.minecraftservices.com/minecraft/client，可使用 -Dminecraft.api.discovery.host 配置。26.3 新增的服务发现接口，用于下发上述各接口的具体地址清单

下表涵括了上面这些服务随着 MC 正式版更新的一些变化，其中相关变更通常最早在对应版本的快照中引入

MC 正式版 Authlib 使用的服务 变化、特点
1.14.4 ~ 1.15.2 1.5.25 auth、account、session 硬编码地址，不可修改
1.16 ~ 1.16.3 1.6.25 auth、account、session 可通过 JVM 系统参数调整地址
1.16.4 ~ 1.20.1 2.1.28 ~ 4.0.43 auth、account、session、services 增加 services
1.20.2 5.0.47 account、session、services 移除 auth
1.20.3 ~ 1.21.8 6.0.52 ~ 6.0.58 session、services 移除 account，玩家档案查询改走 services
1.21.9 ~ 26.2 7.0.61 ~ 9.0.75 session、services、profiles 新增 profiles，玩家档案查询改走 profiles
26.3+ 10.0.77+ discovery 移除上述独立参数，改用 discovery 服务发现

1.16 ~ 26.2：独立参数配置

在 1.16 ~ 26.2 中，Authlib 解析自定义服务地址时，除 1.16.4 ~ 1.20.1 的 services 允许缺省外，要求当前版本所用的核心服务参数必须同时提供才会生效，哪怕只漏掉其中一个，也会全部回退到官方默认地址。因此实际配置时，哪怕我们最关心的只是负责正版入服验证的 session 服务，也必须把其余几个服务一并配齐。直接把前 5 个参数一股脑全带上最省事，一套参数即可兼容 1.16 ~ 26.2 的所有版本

26.3+：discovery 服务发现机制

从 26.3 起，Authlib 改用了服务发现机制，不再读取原先那 5 个 -Dminecraft.api.<service>.host 参数，而是只读取 -Dminecraft.api.discovery.host

这个参数虽然名字还以 .host 结尾，但实际接收的是包含路径的完整 URL，而非仅域名，其官方默认地址为 https://discovery.minecraftservices.com/minecraft/client。Authlib 发起认证等请求时的流程也变成了两步：

  1. 向 discovery 地址发送 GET 请求，拉取一份 JSON 格式的服务地址清单。清单中按服务分类，给出了 session 下的客户端 join 与服务端 verify 接口，以及 profiles、authentication 公钥获取等各个接口的具体请求 URI
  2. 后续进行会话验证、拉取公钥、查询玩家档案等操作时，全部按照清单里给出的 URI 发送请求

这意味着在 26.3+ 中，-Dminecraft.api.discovery.host 只决定了“从哪里拉取清单”。如果转发服务器只是原样反代了官方的 discovery 接口，那么客户端和服务端拿到清单后，后续请求依然会直连官方的 sessionserver.mojang.com 等域名。因此，转发服务必须在返回这份 JSON 清单时，将里面的各个接口地址一并改写为对应的转发服务器地址

那咋整呢

上面这些服务里，虽然最核心的是负责正版入服验证的 session 服务，但考虑到 Authlib 要求各服务成套配置，26.3+ 还需搭配 discovery 服务，既然搞都搞了，那不如全搞上

值得一提

作为一个运作在七层的转发服务器，它是完全有能力截获并篡改转发并请求明文内容的。若你不信任此服务器，请不要使用这一转发服务器

当然，对我而言，我定然是不会干这些坏事的。转发服务器上处理的各种转发请求，也不会持久化于于服务器的日志/文件里，确保数据安全不泄密

这套转发服务的具体实现也已经开源了：https://github.com/Fallen-Breath/pavonis 。不仅能反代 Mojang 的认证服务，还能反代其他各种 HTTP 服务
