SSH 端口转发的延迟问题分析

发表于 2025-06-09 更新于 2026-09-19 分类于 SSH 阅读次数： 本文字数： 4k 阅读时长 ≈ 7 分钟

tl;dr，OpenSSH 的 sshd 只在某个 session 通道跑过 shell、exec 或 subsystem 请求时，才会调用 set_nodelay() 给 ssh 所在的那条 TCP 连接关掉 Nagle。端口转发时若不开 session 通道，服务端就一直不会给这条连接设 TCP_NODELAY

JumpServer 用转发网关做 ssh 中转，和 ssh -N -L 一样都仅启用了 ssh 的端口转发，使得服务端不设置 TCP_NODELAY。 在 RTT 较高的链路上就会出现回包攒批，导致回显一卡一卡的

背景

家里云上部署了个 JumpServer 作为访问各种小鸡的枢纽。JumpServer 有个叫网域的功能， 可以配置一台转发网关做 SSH 中转，用于访问内网服务，也可用于改善到目标服务器的访问质量

前两天给 JumpServer 配了台美西的 CN2-GIA 线路机，作为美国非优化线路小鸡的 SSH 中转。线路本身丢包率很低， RTT 升高后延迟变大也在预期内，但实际用起来却遇到了一个奇怪的问题：打字时回显一顿一顿的，敲下去的字符会攒几个一起冒出来

先看看是不是 JumpServer 在干坏事。JumpServer 的转发网关是借助 SSH 的 Local Port Forwarding 实现的， 它的 SSH 组件叫 koko，里面用的 SSH 库是 x/crypto/ssh，中转逻辑分三步：

  1. 调用 ssh.Dial 连上转发网关，拿到一个 ssh.Client
  2. 调用 ssh.Client.Dial 连接目标节点的 SSH 端口，拿到一条转发后的 TCP 流
  3. 调用 ssh.NewClientConn，在这条流上创建指向目标节点的 SSH 连接

复现

先排除一下 koko 自身的嫌疑，单独验证 golang 的 ssh 转发逻辑

我照着 koko 的中转逻辑写了个最小的 Go 工具：连上转发网关，让网关开一条到目标节点的 direct-tcpip 通道， 再在这条通道上跑一个 SSH 会话，相当于用 Go 重新实现了一遍 ssh -L

工具在本地监听一个端口，验证方式和正常用 JumpServer 一样：另开一个终端从本地端口连进去，进到目标机后长按一个键看回显。 结果在这个小工具上也能稳定复现卡顿，说明问题出在这套转发方式本身，koko 的嫌疑就此排除

为了定位这是 golang ssh 库的问题，还是 OpenSSH 的问题，我尝试直接用纯 ssh 客户端来复现

翻了下转发网关上 sshd 的日志，发现两者在转发上的差别只有一处：ssh -L 在外层连接上开了一个 session 通道， 用来跑登录转发网关的那个 shell，而小工具从头到尾只有 direct-tcpip

可以看到两份日志里都有 fd 3 setting TCP_NODELAY 和 fd 6 setting TCP_NODELAY，其中 fd 3 对应 ssh 所在的那条 TCP 连接， fd 6 则是 -L 在本地监听 accept 出来的连接。也就是说客户端这侧在两种情况下都设好了 TCP_NODELAY， 日志里的差异同样只剩 session 通道这一处

抓包

为什么少一个 session 通道就会导致卡顿呢？先从网络包上找找线索

卡顿表现为“客户端 -> 转发网关”这一跳的回包不连续，而且这一跳的 RTT 也是整条链路上最大的，先在转发网关上抓个包， 把转发网关发往客户端这一个方向的包捞出来：

抓包对象是带 -N 的那条连接。从 2222 端口进去的会话停在 bash 提示符，按住 a 键观察回显，抓到的片段如下：

统计整段 3.17 秒的抓包数据，转发网关发出的数据包大小稳定在 588 到 672 字节，间隔 159 毫秒，中间夹着的纯 ACK 包每 40 毫秒一个。 按 ack 号推算，客户端上行一共发了 13356 字节，平均每 40 毫秒 168 字节，两个方向的总量都在 13.3 KB 左右

按住一个键产生的输入是连续的，回显理应跟着输入连续返回，但抓包里的回显却被攒成了每 159 毫秒一批。同时 ping 转发网关得到的 RTT 是 160 毫秒， 恰好和回包间隔对得上，相当于每个 RTT 才发出一包数据

看到这种等一个 RTT 才攒批发一包的表现，直接怀疑是转发网关这侧的 TCP_NODELAY 没启用，触发了 Nagle 算法。 不过目前还只是猜测，得去翻翻 OpenSSH 的源码确认一下

根因

转发网关的 OpenSSH 版本是 8.7p1，搞一份它的 源码， 在里面搜一波 set_nodelay 的调用点。可以发现，作用在 ssh 所在的那条 TCP 连接上的只有一处，位于 packet.c 的 ssh_packet_set_interactive()：

可以看到 set_nodelay 是无条件执行的，跟 interactive 参数无关，并且 set_interactive_called 保证了这个函数只生效一次。 由于 TCP_NODELAY 是 socket 级别的标志，只要在 ssh 所在的那条 TCP 连接上调用过一次，后续在这条连接上复用的所有通道都会生效

接下来看看 sshd 什么时候会调用这个函数。顺着调用链往上找，服务端只有两处调用，都在 session.c 里， 分别是 do_exec_no_pty 和 do_exec_pty。这两个函数的入口都是 do_exec，而 do_exec 只会由 session 通道上的 shell、exec、subsystem 三种请求触发

服务端收到的请求 服务端的动作 ssh 所在的那条 TCP 连接上的 TCP_NODELAY
session 通道 + shell / exec / subsystem 进入 do_exec 设置
session 通道 + pty-req 分配 pty 维持默认
direct-tcpip 在 connect_next 里给出站 socket 设置 维持默认

到这里，现象和代码就完全对上了。开过 session 通道并且跑过命令的 ssh 连接会设置 TCP_NODELAY，而只做端口转发的 ssh 连接 则一直开着 Nagle，导致服务端回包被攒成了一个 RTT 一批

其实端口转发逻辑里也有设置 TCP_NODELAY 的地方，只是设到了别的 socket 上：转发网关连向目标机的出站 socket 在 channels.c 的 connect_next 里设置了，客户端 -L 在本地监听 accept 出来的连接也单独设置了，偏偏漏掉了客户端与转发网关之间那条承载 ssh 的 TCP 连接本身

至于为什么只有转发网关发往客户端的下行方向被卡住，而客户端发往转发网关的上行方向一直正常，是因为 koko 那侧用的是 Go 的 net.TCPConn， 在创建连接时 newTCPConn 默认就调用了 setNoDelay(true)

解决方法

原因清楚了，解决思路也就很直接：只要让 ssh 所在的那条 TCP 连接上出现一次 session 通道的 shell、exec 或 subsystem 请求，转发网关的 sshd 就会把 TCP_NODELAY 设上。因此在 SSH 连接建立之后，可以先开一个 session 通道并请求一个 shell，再去建立后面的端口转发通道

如果平时手动用 OpenSSH 客户端做端口转发，去掉 -N 参数也是同样的效果：外层连接建立时会顺带开一个 shell， 触发转发网关的 sshd 给这条 TCP 连接设上 TCP_NODELAY

  • 转发网关：RHEL 9.5 自带的 OpenSSH_8.7p1
  • koko 版本：v4.10.1-ce
  • GoLang 版本：1.24.1

参考

搜这个问题的时候也翻到了几处古早的社区记录，时间跨度挺大，看来这个行为在 OpenSSH 里已经存在二十多年了：

  • 2002 年的 openssh 邮件列表 里讨论过给 Nagle 加一个开关，也有人提出转发的 TCP 端口和 X11 应该关掉 Nagle，不过这个改动最后没有合进代码

  • 2003 年的 openssh bug 556 提到的就是端口转发时 TCP_NODELAY 只设到了转发端口上，导致服务端发往客户端的数据被缓存并形成 bursting effect，这个 issue 的状态至今仍是 NEW
