Gradle daemon 在构建结束后持续占用内存带宽的问题分析

发表于 2026-11-02 分类于 Minecraft 阅读次数： 本文字数： 7.6k 阅读时长 ≈ 14 分钟

在 fabric-mod-template 里增删子项目或修改子项目的 Minecraft 版本后， 有时哪怕只跑一次 gradlew，等命令跑完退出，整机的内存读取带宽依然会稳定在 29 GB/s 左右，写入带宽也有约 26 GB/s。 手动把 Gradle daemon 停掉后，带宽便立刻回落。手头多台 Windows 开发机上都遇到过这个怪现象

tl;dr，旧版 Xray 的 Vision 在连接关闭时会多送一条 TLS 记录， 导致 Fabric Loom 所用的 JDK HttpClient 卡进一个不断分配缓冲区的死循环里。升级 JDK 或升级 Xray 服务端均可解决

环境

先列一下基本环境：

  • Windows，多台开发机均可复现
  • Gradle 9.8.2，daemon 运行在 Oracle JDK 25.0.2 上
  • Fabric Loom 1.19.3
  • 经本机 Xray 客户端提供的 HTTP 代理上网，节点使用 VLESS + xtls-rprx-vision。Xray 客户端版本为 26.10.21，服务端版本为 26.3.27

分析

分配热点

先用 jcmd 找到出问题的 Gradle daemon 进程，隔几十秒抓两次带扩展信息的线程栈，顺带录一段 20 秒的 Java Flight Recorder（JFR）。 JFR 是 JDK 自带的低开销采样工具，可以记录对象分配、GC 等事件，刚好适合拿来查是谁在狂吃内存带宽：

两次线程栈相隔约 36 秒，对比下来可以看到其中一个工作线程 ForkJoinPool-1-worker-2 的 CPU 时间涨了约 35 秒，基本吃满了一个核心。 Java 的虚拟线程并不独占系统线程，而是挂载在 ForkJoinPool 的工作线程上运行。 两次采样时，这个工作线程上跑的都是同一个虚拟线程，正在执行 JDK HttpClient 的 TLS 读取代码

JFR 的结果更加直观：这个线程在 20 秒内分配了 458 GiB 的对象，折合下来约 23 GiB/s。 在全部 5,913 个对象分配样本里，有 5,909 个都是这个虚拟线程顺着同一条调用路径分配出来的 byte[]：

SSLFlowDelegate 是 JDK HttpClient 内部负责处理 TLS 收发的组件， 里面的 Reader 会把从 socket 读到的密文交给 TLS 引擎 SSLEngine 解密，这一步叫 unwrap， 而 getAppBuffer() 则负责为每次 unwrap 申请一块存放解密后明文的输出缓冲区

这些缓冲区刚一分配出来就立刻被丢弃，短短 20 秒内 G1 就做了 194 次年轻代 GC 来回收它们。 所以虽然进程的内存占用看着只有几 GiB，但背后持续不断的内存分配和清零已经把整机的内存带宽吃满了

请求来源

线程栈里只能看到 JDK 内部的异步任务，看不出是谁发起了这个 HTTPS 请求。 于是用 jcmd 18472 GC.heap_dump -all heap.hprof 搞了一份堆快照下来， 从出问题的 Reader 顺着对象引用往回摸，找到它所属的 HttpClientImpl，再找持有这个客户端的对象， 最终定位到了 Fabric Loom 1.19.3 下载器里的静态字段 net.fabricmc.loom.util.download.Download.HTTP_CLIENT

翻看堆里的数据，这条连接请求的目标是 piston-data.mojang.com，也就是 Loom 用来下载 Minecraft 资源的服务器，下文简称资源服务器。 连接通过本机的 HTTP 代理以 CONNECT 方式建立：代理只负责在两端之间原样转发字节，TLS 加密仍在 Java 与资源服务器之间端到端进行， 协商出来的协议为 HTTP/2 和 TLS 1.3

到这里也就解释了为什么只跑一次 gradlew 就能触发。Gradle 在配置项目时会执行各个子项目的构建脚本， Loom 在这一阶段就会按脚本里声明的 MC 版本去准备依赖。版本改动后，本地缺失的资源就会在这时下载。 等到命令结束后，Gradle daemon 依然留在后台继续存活，这次下载留下的 HttpClient 后台任务也就跟着一直留在 daemon 里了

停不下来的读取循环

堆快照里还保留着这条连接的关闭状态。先简单说明一下其中涉及的两个关闭信号：

  • GOAWAY 是 HTTP/2 的帧，表示对端不再接受新请求，准备关闭连接
  • close_notify 是 TLS 层的关闭通知，以一条 alert 告警记录的形式发送。 TLS 引擎收到它之后就会关闭输入方向，后续再调用 unwrap 都只会一律返回 CLOSED，不再消费任何输入

除此之外，Reader 还维护着一个自己的完成标记 completing。只有当上游，也就是 socket 一侧通知数据流结束后，它才会变成 true。 这里的数据流结束指的就是 socket 读到了 EOF，即对端关闭了 TCP 连接

从堆快照里捞出来的现场值如下：

对象 字段 现场值
HTTP/2 连接 是否收到 GOAWAY、活动请求数 已收到，0
TLS 引擎 是否收到 close_notify、最近一次 unwrap 的结果 已收到，CLOSED
Reader 输入缓冲区 readBuf 的 position / limit 0 / 24
Reader minBytesRequired 0
Reader completing false
SSLFlowDelegate 每次申请的输出缓冲区大小 16384

可以看到，从 HTTP/2 和 TLS 两层来看，这条连接其实都已经结束了，偏偏 Reader 的输入缓冲区里还剩着 24 字节没处理， 底层 socket 也还没读到 EOF。JDK 25.0.2 中 Reader.processData() 的主循环简化后如下：

现场的这组状态刚好把这段逻辑给卡死了：TLS 引擎已经关闭，每次 unwrap 都不消费那 24 字节，导致循环条件 24 > 0 永远成立； 而唯一的退出分支又要求 completing 为 true，偏偏它始终是 false。 结果每一轮循环都白白申请一块 16 KiB 的缓冲区然后丢掉，这正是前面 JFR 里抓到的那条分配路径

为了确认光凭这个状态就足以单独造成空转，我在独立的 JVM 里直接构造了一遍这个现场：把 SSLEngine 关掉，再往还没完成的 Reader 里塞进 24 字节， 全程不联网，也不涉及 Gradle 和 Loom。在 JDK 17.0.18、21.0.10、25.0.2 上跑下来，全都在 500 毫秒内分配了 6 GiB 以上的内存，调用栈与现场完全一致

接下来就得弄清这 24 字节是怎么来的了：既然 TLS 都已经收到了 close_notify，对端理应不会再发来任何数据才对

多出来的 24 字节

排查到这里注意到一个线索：所有能复现问题的开发机都是经 Xray 的 HTTP 代理上网的。于是照着 Loom 的配置， 用 JDK HttpClient 配合虚拟线程执行器写了个单文件测试程序，从资源服务器下载一个约 4.5 MiB 的资源文件， 下载完成后不退出、继续持有客户端，看看连接关闭时到底发生了什么。测试程序的完整代码附在文末

要想复现，首先得让连接由资源服务器主动关闭。JDK HttpClient 默认会在 HTTP/2 连接空闲 30 秒后自己把连接关掉，那样就看不到对端的关闭过程了。 因此实验里把 jdk.httpclient.keepalive.timeout 调到了 120 秒，在下载结束约 90 秒后，就能稳定等到资源服务器发来的 GOAWAY 和 close_notify

至于 Gradle 现场走的则是另一条时序：从堆中 HTTP/2 帧解码器的状态来看，资源服务器的 GOAWAY 在最后一个响应传完之前就已经到了， 所以连接随着最后一个请求结束直接进入了关闭流程，没有经过 30 秒的空闲计时。不过不管走哪条时序，最终都会落到同一个 TLS 关闭过程上

拿同一个测试程序分别跑三条网络路径。除了直连和 Xray 之外，我还手搓了一个普通的 HTTP CONNECT 转发器，它只负责在两端之间原样复制字节， 用来区分问题到底是出在“经过 HTTP 代理”上，还是出在“经过 Xray”上：

网络路径 收到 close_notify 之后 下载结束后第 90–95 秒的 JVM 分配量
直连 读到 EOF，连接关闭 约 0.003 MiB
普通 CONNECT 转发器 读到 EOF，连接关闭 约 0.003 MiB
Xray 又收到 24 字节，开始空转 约 38 GiB

三条路径都完整下完了文件，也都收到了 close_notify，差别只出现在收到 close_notify 之后：直连和普通转发器紧接着就读到了 EOF，唯独走 Xray 的路径又多收到了 24 字节，随后开始空转

为了看清这 24 字节到达的具体时机，我用 --patch-module 给测试 JVM 里的 SSLFlowDelegate 加了两处日志： 用 TLS_CLOSE_TRACE 记录 unwrap 返回 CLOSED 时输入缓冲区的变化，其中的 before 和 after 分别是 unwrap 前后缓冲区的 position/limit；再用 TLS_POST_CLOSE_INPUT 记录关闭之后上游又送来的新数据。 走 Xray 时，打出来的日志如下：

第一行对应资源服务器发来的 close_notify，这 24 字节被完整消费，缓冲区读到了末尾 63/63。 紧接着第二行，上游又单独送来了一段 24 字节的新数据，且此时还没有读到 EOF。从第三行开始，已经关闭的 TLS 引擎面对这段数据只会返回 CLOSED、消费 0 字节，并从此不断重复。 这正是前面在 Gradle 现场堆里看到的状态

把这 24 字节捞出来看一眼。TLS 是以记录为单位传输数据的，每条记录都以 5 字节的记录头开头，依次是内容类型、协议版本和长度。 这 24 字节的记录头是 17 03 03 00 13，代表着一条后跟 19 字节密文的加密记录， 长度跟前一条 close_notify 一模一样，也与 TLS 1.3 下一条加密告警的大小相符。 换句话说，在收到资源服务器的 close_notify 之后，代理路径上又凭空冒出了一条 TLS 告警

根因

Xray Vision 泄漏的外层关闭通知

VLESS 协议在 Xray 客户端和 Xray 服务端之间有一层自己的 TLS，这里不妨称之为外层 TLS； 而 Java 与资源服务器之间的 HTTPS 则是被它承载的内层 TLS。 Vision 流控在识别出内层是 TLS 1.3 后就会切换到 direct copy 模式：两端直接绕过外层 TLS，在底层 TCP 连接上原样转发内层的字节， 以此省去一次加解密开销

问题就出在旧版实现切换到 direct copy 之后，外层 TLS 对象依然留着。 等到连接收尾时，Xray 服务端照常去关闭这个外层 TLS 对象，它便往同一条底层 TCP 连接里写出了一条外层的加密 close_notify。 此时的 Xray 客户端正按 direct copy 模式原样转发字节，根本分不清这条记录其实不属于内层，于是直接把它转交给了 Java。这就是那多出来的 24 字节的来历

翻了下 Xray 的仓库，issue #6794 详细分析过这个问题， 那边复现时抓到的同样是 17 03 03 00 13 外加 19 字节。 随后的修复 PR #6834 在切换到 direct copy 后抑制了外层的关闭通知， 于 2026 年 9 月合并，首个包含该修复的版本是 26.9.30

回头看本次现场的环境，本机的 Xray 客户端 26.10.21 已经包含了修复，但远端的服务端 26.3.27 还没有。 由于这条记录是由服务端写出、沿着下行方向发往客户端的，所以必须升级服务端才能解决。 把服务端升级到 26.10.31 后，再用同一个测试程序经 Xray 下载，收到 close_notify 后便直接读到了 EOF，第 90–95 秒的分配量也回到了正常的约 0.094 MiB

JDK HttpClient 的上游修复

按 TLS 1.3 规范 RFC 8446 §6.1 的要求，收到关闭告警之后到达的数据应当一律忽略。 大多数 TLS 实现都是照此处理的，所以平时就算多出这么一条记录也通常无人察觉，偏偏 JDK HttpClient 还会继续处理缓冲区里剩下的数据，进而一头卡进了前面那个死循环里

JDK 上游其实也已经修掉了这个问题，对应 issue 为 JDK-8374557 “Enhance TLS connection handling”。 补丁在 unwrapBuffer() 处理 CLOSED 的分支里加上了两行代码：

一旦 TLS 输入方向关闭，剩余的输入就会被直接丢弃，同时 Reader 进入完成状态，外层的循环条件也就不再成立了。此外补丁也一并调整了收到 close_notify 后的关闭流程。 该修复目前已合入 JDK 主线，并回移到了 11.0.31、17.0.19、21.0.11、25.0.3 和 26.0.1，各分支的提交见文末参考。 本次现场所用的 25.0.2 刚好不含这个修复。修复版 JDK 我没有在本机复测

故障链路

把整个过程串起来，完整的故障链路如下：

  • Xray 服务端是问题的触发方：代理往内层字节流里混入了不属于它的数据，属于实现缺陷，已在 Xray 26.9.30 中修复
  • JDK HttpClient 是问题的放大方：在输入没有进展时既不退出也不报错，把一条多余的记录放大成了持续的内存分配，同样属于实现缺陷， 已在 JDK 11.0.31、17.0.19、21.0.11、25.0.3、26.0.1 中修复
  • Fabric Loom 和 Gradle daemon 则是躺枪的载体：Loom 只是在配置阶段正常发起下载，而常驻的 daemon 让异常线程在构建结束后继续存在。 作为使用方，他俩都没有 bug

修好 Xray 或 JDK 中的任何一方，这条故障链路都会断开，也就不会再遇到本文描述的问题了

影响范围

要遇到这个问题，需同时满足下面三个条件。下表中的起始版本是翻阅上游源码推算得出的，早期版本未经实测：

组件 起始版本 修复版本
Xray 服务端 1.6.2（2022 年 10 月） 26.9.30
JDK 11（java.net.http 正式发布） 11.0.31、17.0.19、21.0.11、25.0.3、26.0.1
Fabric Loom 0.13.1（2022 年 7 月） 不涉及
  • Xray 在 1.6.2 首次引入了 Vision，从初版起就已经在切换到 direct copy 后保留了外层 TLS 对象，外层无论使用 TLS 还是 REALITY 均受影响
  • JDK 的这个读取循环早在 JDK 10 的孵化版 HTTP Client 中就已经存在，到了 JDK 11 随正式的 java.net.http 模块一并转正
  • Loom 则从 0.13.1 起改用 JDK HttpClient 来下载资源

算下来，这三个条件同时具备最早是在 2022 年 10 月 Xray 1.6.2 发布的时候。 即便不使用 Loom，其他经过 Vision 代理调用 JDK HttpClient 的 Java 程序也同样会遇到这个问题，文末参考里的几份社区反馈都属于这种情况

自查与处理

如果怀疑自己也遇到了这个问题，可以在 daemon 上跑一下 jcmd <pid> Thread.print -e。要是看到某个线程的 allocated= 已经达到了数百 GB 乃至 TB 级别， 并且调用栈停在 SSLFlowDelegate$Reader.unwrapBuffer，那基本就是它没跑了

处理方式二选一即可：

  • 把 Gradle daemon 所用的 JDK 升级到 11.0.31、17.0.19、21.0.11、25.0.3、26.0.1 或更新版本。 daemon 实际使用的 JDK 由 gradle.properties 中的 org.gradle.java.home、IDE 的 Gradle JVM 设置或 daemon JVM toolchain 决定， 都没指定时则默认沿用启动 gradlew 的 JDK，即 JAVA_HOME。可以用 jcmd <pid> VM.version 来确认 daemon 实际跑在哪个版本上
  • 如果代理节点用了 Xray Vision，把 Xray 服务端升级到 26.9.30 或更新版本

至于已经卡进死循环里的 daemon 是不会自行恢复的，跑一下 gradlew --stop 或直接结束进程即可
